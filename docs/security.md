# QueryLens Security Architecture & Guarantees

This document details the security principles, authorization boundaries, and runtime execution protections enforced across QueryLens.

## 1. Authentication, CSRF, and Tenant Isolation

- **Private Ownership:** All database connections, catalog snapshots, semantic metrics/labels, saved questions, and query runs are strictly owner-scoped by `user_id`.
- **Tenant Isolation:** Foreign resources return HTTP 404 (not 403) to prevent unauthorized enumeration or information disclosure.
- **CSRF Protection:** All state-changing requests (`POST`, `PUT`, `PATCH`, `DELETE`) require a valid session-bound synchronizer token via the `X-CSRF-Token` header.
- **Origin Validation:** Requests must originate from configured allowed origins.
- **Credential Storage:** Database passwords and sensitive connection parameters are encrypted at rest using envelope encryption with active keyring management. Credentials are decrypted only inside isolated execution workers and never logged or exposed via APIs.

## 2. Read-Only SQL Policy & AST Verification

Every SQL query submitted to QueryLens (whether generated by an LLM, manually edited by an authorized user, or rerun via saved question parameters) undergoes strict AST-level policy verification using `sqlglot`:

- **Single Statement Only:** Semicolon-delimited batches, script execution, and multiple statements are rejected before execution.
- **Read-Only Construct Enforcement:** DDL (`CREATE`, `ALTER`, `DROP`, `TRUNCATE`), DML writes (`INSERT`, `UPDATE`, `DELETE`, `MERGE`), and procedural blocks are strictly prohibited.
- **Function Allowlist:** Only verified read-only scalar and aggregate functions are permitted. Administrative, locking (`FOR UPDATE`), sleep (`pg_sleep`), filesystem, and network functions are rejected.
- **Catalog Scope Authorization:** Queries can only access tables and columns explicitly allowed in the connection's `allowed_tables` configuration. References to unlisted tables or hidden system catalogs (`pg_catalog`, `information_schema`, `mysql`) are rejected before execution.

## 3. Parameter Compilation & Driver Binding Guarantees

QueryLens eliminates SQL injection risks through immutable, typed DBAPI driver bindings:

- **Zero String Interpolation:** Filter values and dates are never interpolated or concatenated into SQL text.
- **Driver Parameter Syntax:** Named slots are compiled to DBAPI pyformat `%(param_name)s` for both PostgreSQL (`psycopg`) and MySQL (`PyMySQL`).
- **Literal Escaping:** Any literal `%` characters in queries (such as `LIKE 'foo%'`) are safely escaped to `%%`.
- **Immutable Capability Tokens:** Validated queries produce an immutable `ValidatedQuery` token containing compiled SQL and `bindings: tuple[BoundParameter, ...]`.
- **Deterministic Token Fingerprinting:** `compute_token_fingerprint` hashes the canonical SQL, bindings, connection ID, engine, policy version, snapshot hash, and row caps using SHA-256. `SafeExecutor.execute` verifies this signature before accessing database credentials.

## 4. Direct Execution Isolation (Zero LLM Provider Calls)

Manual SQL editing (`POST /api/v1/queries/sql`) and saved question execution (`POST /api/v1/saved-questions/{id}/run`) follow direct, deterministic execution paths:
- They bypass prompt assembly, schema selection, and LLM generation entirely.
- Zero LLM provider or query repair calls occur on these paths.
- Execution is bounded by strict row limits (1,000 max), UTF-8 SQL size limits (32,768 bytes max), and execution deadlines (30s max).

## 5. Source Network & Sandbox Boundaries

- Connections are limited to configured engines (PostgreSQL, MySQL).
- Database connections use read-only transactions where supported by the driver.
- Execution runs inside managed worker pools with active lease tracking and cancellation via thread/socket termination.
